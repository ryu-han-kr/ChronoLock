# ChronoLock 0.2 — 새 기능과 사용 안내

작성: 2026-10-13. Android 오프라인 기능 확장입니다. 월 990원은 출시 가격 결정이며 실제 결제는 아직 연결하지 않았습니다.

## 무엇을 추가했나요?

| 기능 | 해결하려는 문제 | 사용 예시 |
|---|---|---|
| 1회 사용시간 제한 | 하루 한도 안에서도 한 번 열면 너무 오래 사용하는 문제 | YouTube를 한 번에 5분까지만 사용 |
| 요일·시간대 예약 | 매일 같은 시간에 수동으로 제한을 바꾸는 번거로움 | 월~금 23:00부터 다음 날 07:00까지 차단 |
| 빠른 집중 모드 | 지금 할 일에 집중하려고 앱마다 따로 설정하는 번거로움 | 제한이 켜진 앱들을 25·50·90분 동안 함께 차단 |
| 집중 레시피 3종 | 숫자와 규칙을 처음부터 조합하기 어려움 | 짧게 보고 쉬기 / 확인 횟수 줄이기 / 취침 시간 지키기 |
| 최근 7일 리포트 | 오늘만 보고 사용 습관을 판단하는 문제 | 날짜별 기록 사용시간, 전체 사용량·실행 횟수 확인 |
| 기록 기반 설정 제안 | 자신의 반복 사용 패턴에 어떤 제한이 맞는지 모르는 문제 | 짧게 자주 열면 횟수 제한, 오래 쓰면 1회 한도 제안 |
| 규칙 일시 중지 | 설정을 지우지 않고 잠시 쉬고 싶을 때 | 앱 설정에서 ‘제한 사용’을 끄고 나중에 다시 켜기 |

핵심은 **짧게 사용 → 충분히 쉬기 → 기록 확인 → 필요한 제한만 보완하기**입니다. 서버나 유료 AI 호출 없이 기기 안에서 동작합니다. 저장된 규칙을 추천이 자동으로 변경하지 않습니다.

## 1. 한 번에 사용할 시간 정하기

1. **앱 제한 → 대상 앱의 설정**을 엽니다.
2. **한 번에 허용할 시간(초)**에 입력합니다. 300초는 5분입니다.
3. 필요하면 **종료 후 재실행 대기(초)**도 함께 입력하고 저장합니다.

한도에 도달하면 차단을 유지합니다. 앱을 떠난 뒤 새로 진입하면 새 사용 세션을 시작하며, 쿨다운·일일 한도·실행 횟수 등 다른 제한도 함께 검사합니다. 즉시 재진입을 줄이려면 쿨다운을 함께 설정하세요. 차단 시점부터 사용량 계측을 멈추므로 차단 화면을 보고 있는 시간을 계속 더하지 않습니다.

같은 부팅에서 서비스가 다시 연결되고 동일 앱이 계속 감지되면 저장한 차단 세션을 복구합니다. 다른 앱으로 이동했거나 기기를 재부팅한 경우에는 기존 세션을 종료한 것으로 처리합니다. 서비스 중단 중 실제 앱 전환은 완전히 재구성하지 못하므로 실기기 감지 복구 검증은 별도입니다.

## 2. 취침·공부 시간 예약하기

**앱 설정 → 요일·시간 예약**을 켠 뒤 요일, 시작, 종료를 입력합니다.

- 시각 형식은 `23:00`처럼 24시간제 `HH:mm`입니다.
- 선택한 요일은 **차단이 시작하는 날**입니다.
- 월요일 `23:00~07:00`은 월요일 밤부터 화요일 아침까지입니다.
- 시작 시각은 포함하고 종료 시각에는 예약 차단을 해제합니다. 다른 제한이 남아 있으면 차단은 계속됩니다.
- 앱을 계속 열고 있어도 주기적으로 검사해 예약 시작·종료를 반영합니다.
- 같은 시작·종료 시각, `24:00`, 잘못된 분, 선택한 요일이 없는 설정은 저장을 거부합니다.
- 현재 기기의 현지 시각·시간대를 따르며 앱별 예약 구간은 하나입니다.

## 3. 지금부터 25·50·90분 집중하기

**오늘 → 지금부터 집중**에서 시간을 선택하면 대상 앱 목록을 확인한 뒤 시작합니다.

- 시작할 때 **제한이 켜진 기존 앱들**에만 적용합니다. 집중 중 새로 추가한 앱은 이번 집중에 포함되지 않습니다.
- 앱의 기존 규칙과 별도로 집중 종료 시각을 저장합니다. 앱을 다시 열거나 기기를 재부팅해도 아직 남은 시간에 대한 제한을 판정할 수 있습니다.
- 남은 시간을 표시하며 **집중 종료**로 언제든 취소할 수 있습니다.
- 종료하거나 시간이 만료되어도 기존 일일 한도·횟수·쿨다운·예약은 유지됩니다.
- 대상 앱이 없거나 권한·감지 연결이 준비되지 않으면 시작 버튼을 비활성화합니다.
- 집중 중 규칙을 편집해도 집중 종료 시각이 사라지지 않도록 보호합니다. 규칙을 끄거나 삭제하는 일반 모드의 권한은 유지됩니다.

현재는 완료 알림·누적 집중 성과·집중 기록 전용 화면까지 제공하지 않습니다. 시스템 시각을 직접 바꾸면 절대 시각으로 저장한 종료 시점에도 영향을 줍니다.

## 4. 레시피로 시작하기

앱 설정 상단에서 레시피를 선택하면 아래 입력값을 미리 채웁니다. **선택만으로 저장되지 않으며**, 내용을 확인하고 저장해야 적용됩니다.

| 레시피 | 채워지는 값 |
|---|---|
| 짧게 보고 쉬기 | 1회 300초 + 종료 후 600초 대기 |
| 확인 횟수 줄이기 | 하루 5회 + 1회 180초 |
| 취침 시간 지키기 | 매일 23:00~다음 날 07:00 예약 |

일반 레시피 버튼은 입력 중인 제한 조합을 교체합니다. 아래의 기록 기반 제안은 이와 달리 기존 제한을 보존합니다. 입력 화면은 세로로 스크롤할 수 있으며 화면 상태 복원 시 입력값을 유지하도록 구성했습니다.

## 5. 최근 7일 기록과 맞춤 제안

오늘 화면 아래에서 오늘을 포함한 7일의 기록을 확인합니다. 기록이 없는 날짜는 ‘기록 없음’으로 표시하며 사용하지 않았다고 단정하지 않습니다.

추천은 활성 규칙이 있는 앱의 7일 내 기록을 사용하며, **3일 이상·15회 이상 실행·사용량 0초 초과**일 때 후보를 만듭니다.

- 기록 사용량 ÷ 허용 실행 횟수가 평균 2분 이하이고 횟수 제한이 없으면 **확인 횟수 줄이기**를 제안합니다.
- 평균 5분 이상이고 1회 한도가 없으면 **짧게 보고 쉬기**를 제안합니다.
- 후보가 여러 개면 실행 횟수가 가장 많은 앱 하나를 보여줍니다.
- **제안 살펴보기**는 기존 일일 한도·예약·이미 설정한 한도를 그대로 두고 비어 있는 항목만 채웁니다. 확인 후 저장해야 적용됩니다.
- 추천 근거인 기록 일수·실행 횟수·실행당 기록 사용시간을 함께 표시합니다.

이는 관측 기록에 대한 간단한 규칙 기반 제안입니다. 실제 개별 세션 평균이나 의료적·심리적 진단이 아니며, 누락된 기록이 있으면 근거 수치도 불완전합니다. 절약한 시간이나 집중 점수를 임의로 만들어 표시하지 않습니다.

## 6. 기존 데이터와 업데이트

- 앱 버전은 `0.2.0` / versionCode `2`입니다.
- Room DB를 v1에서 v2로 올리며 기존 규칙·사용량·체크포인트를 유지합니다. 새 기능 필드는 기본적으로 비어 있고 이전 차단 여부는 false로 시작합니다.
- 추가 저장 항목: 1회 한도, 예약 시각·요일, 집중 종료 시각, 관측 중인 앱·차단 세션 사용량·차단 상태.
- 같은 앱의 차단 상태를 복원할 때 오버레이 뒤 앱의 시간을 다시 사용량으로 더하지 않고, 차단 시도도 중복 기록하지 않게 했습니다.
- 인터넷 권한·로그인·API 키·신규 서버가 필요하지 않습니다.

이전 APK 위에 설치하려면 패키지와 서명키가 같아야 합니다. CI Debug APK는 실행마다 서명키가 달라질 수 있으므로 실제 기존 설치의 업데이트 가능 여부는 별도 확인해야 합니다. DB 이전 테스트는 실제 업데이트 설치·서명 검증과 다릅니다.

## 검사 계획과 결과

기존 41개 단위 테스트에 입력 검증·레시피·복구·예약 경계·기록 추천 테스트 20개를 추가했습니다. Room 테스트에는 설정 저장·집중 종료 시각·차단 세션·v1 DB 이전 검사를 추가했고 Compose UI 테스트도 구성했습니다.

| Room 통합 | 실제 파일 DB 재개방, v1→v2 이전, 집중 시작·취소·종료 | Android 35 계측 보고서 |
| Compose UI | 레시피 미리보기·저장, 잘못된 예약 거부, 집중 버튼·카운트다운, 입력 상태 복원 | Android 35 계측 보고서 |
| 빌드·Lint | APK, 계측 APK, 정적 검사 | GitHub Actions |
| 시각 확인 | 편집창·집중 시작·진행 화면 캡처 | CI `android-device-reports`의 `screenshots/` |
| 실제 기기 | 앱 전환·오버레이·잠금·재부팅·배터리 절약 | 별도 확인 필요 |

최신 완료 결과와 빌드 링크는 [STATUS.md](STATUS.md) 및 PR 검증 기록을 기준으로 합니다. 코드에 검사가 있다는 이유로 실행 통과로 간주하지 않습니다.
